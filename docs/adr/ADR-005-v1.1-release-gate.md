# ADR-005: v1.1 Release Gate Design

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-08-24 |
| Relates to | ADR-001 (POC v1.1), ADR-002 (event-sourced accountability) |
| Scope | `.github/workflows/v1.1-release-gate.yml`, branch protection |

## Context

POC v1.1 spans three independently-built artifacts — the Python platform (observation layer, governance/lineage/evidence subsystems), the framework-agnostic `observation-client` (TypeScript), and the React dashboard — plus cross-cutting invariants that no single package's test suite can prove alone: reducer equivalence across languages, and sequence durability under concurrency. Phase B's audit established that these invariants are release-blocking, and the constitution requires layered verification and fail-closed security posture.

## Problem

Define a CI structure such that **no v1.1 artifact can be released unless every contractual, durability, and equivalence invariant is empirically verified**, while satisfying:

1. **Fail-closed** — any single gate failure blocks release; there must be one unambiguous signal for branch protection.
2. **Constitutional independence** — each subsystem is verified in isolation (single responsibility, independent testing), never as one monolithic test run.
3. **Efficiency** — independent gates run in parallel; expensive gates (Postgres integration, Docker builds) run only when their cheap prerequisites pass.
4. **Traceability** — coverage, test results, and build artifacts must be attributable per gate.

## Decision

A six-job directed acyclic graph with a dedicated **aggregate job** as the single branch-protection check:

```
observation-client ──────────────────────┐
                                         ▼
platform-unit ──► platform-integration ──┼──► dashboard ──► release (main/tag only)
                                         │
                                         └──► aggregate (always runs; single signal)
```

Rules encoded in the workflow:
- `platform-integration` **needs** `platform-unit` — no Postgres compute is spent if unit tests fail.
- `dashboard` **needs** `observation-client` — the `file:` dependency resolves to a *verified* build artifact, never to whatever is on disk.
- `release` runs only on `main` or `v1.1.*` tags and **needs** both durability (Gate 3) and presentation (Gate 4).
- `aggregate` runs `if: always()`, inspects `needs.*.result`, renders a gate matrix into `$GITHUB_STEP_SUMMARY`, and exits non-zero unless every gate is `success`.
- `concurrency: cancel-in-progress` per ref prevents stale runs from consuming compute or producing ambiguous signals.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Single monolithic job running everything sequentially | Violates subsystem independence; one flaky step obscures which invariant failed; no parallelism; slow critical path |
| Per-package independent workflows, no aggregate | Branch protection would require listing N checks; no single fail-closed signal; adding a gate changes repo config |
| Matrix build over packages | Gates are heterogeneous (different services, dependencies, ordering constraints); a matrix forces artificial uniformity |
| Require all four gate checks individually in branch protection | Works, but couples protection rules to job names; aggregate decouples them and gives one human-readable verdict |

## Trade-offs

- **One extra job** (aggregate) in exchange for a single protection check and a rendered summary — cheap.
- **Longer critical path** than fully parallel (integration waits for unit) — deliberate: compute is spent only on trustworthy prerequisites.
- **Docker builds only on main** mean PR authors don't get image-level feedback — accepted: the Dockerfile exercises no logic beyond copying an already-verified `dist/`; image correctness is re-verified on merge.
- **`if: always()` on aggregate** is subtle: a cancelled upstream job reports `cancelled`, which the failure condition correctly treats as not-success. This must be preserved if the condition is ever edited.

## Benefits

1. Fail-closed by construction: release is impossible unless all gates report success.
2. Constitutional alignment: each subsystem tested independently; the pipeline itself is a collection of loosely coupled, independently replaceable jobs.
3. Adding a gate (e.g., mutation testing) is one new job plus one entry in `aggregate.needs` — no restructuring, no branch-protection change.
4. Artifacts (coverage, dist, integration results) are uploaded per gate, giving full traceability for any failure.

## Risks

| Risk | Mitigation |
|---|---|
| `aggregate.needs` list drifts when gates are added/renamed | The gate matrix in the summary makes omissions visible; document the rule in the workflow header |
| Postgres service container flakiness | Healthcheck with 20 retries plus an explicit `pg_isready` wait loop before tests |
| `release` job could run with a stale artifact if needs-list is mis-edited | `needs: [platform-integration, dashboard]` is explicit; aggregation fails closed on any non-success |
| Secrets/permissions creep | Minimal permissions declared (`contents: read`, `packages: write`); push only via ephemeral `GITHUB_TOKEN` |

## Future evolution considerations

- **v1.2 mutation-testing gate** (constitution: "mutation testing where appropriate").
- **Security gates**: dependency audit, SBOM generation, image signing (SLSA provenance) — constitution's supply-chain integrity requirement.
- **Performance regression gate** once fitness baselines exist.
- Extract jobs into **reusable workflows** when other platform repos need the same gates.
